## 一、测试例怎么驱动评测（数据流）

```
测试例 test_case                  版本 version
├─ input_payload (业务数据)        ├─ config_payload.system_prompt_template (改写指令模板)
│   ├─ name        (达人名)        │   含 {{persona}} {{product_info}} {{original_script}} 占位符
│   ├─ persona     (达人人设)       │
│   ├─ product_info(产品信息)       │
│   └─ original_script(参考脚本)    │
├─ tags (场景标签)                 │
└─ name/description (管理用)       │
        │                          │
        └──────────┬───────────────┘
                   ▼
         generator.py 渲染：模板里的 {{persona}} ← input_payload['persona']，{{product_info}} ← input_payload['product_info'] …
                   ▼
         generator.py:88 → AI(yunwu/glm/kimi) 生成仿写文案
                   ▼
         scorer 四维打分 → 落库
```

**关键**：「**改写指令**」存在**版本提示词模板**里（`version.config_payload.system_prompt_template`），**不在测试例里**。测试例只提供「喂给指令的业务素材」。

## 二、发现的问题：`messages` 是个死字段

现在 demo seed（`seed_eval_demo.sql` / `seed_eval_testcases_demo.py`）在 `input_payload` 里塞了一个 `messages` 字段（一句"仿写 XX 千川文案…"的指令）。

**但全系统没有任何代码读它**。证据：

- `generator.py:80-88`：prompt = 渲染版本模板（占位符取值来自 input_payload 的 name/persona/product_info/original_script），然后 **`generate_fn(messages=[{"role":"user","content":渲染后prompt}])`** —— messages 是 generator **自己造的**（固定一条 user 消息），**不取 input_payload['messages']**。
- runner / scorer 都不读 `input_payload['messages']`。

所以 `messages` 是早期遗留的冗余字段，**对评测执行毫无影响**。这正好印证我们之前定的架构（已写入项目 memory `eval-testcase-vs-prompt-split`）：**测试例 = 纯业务数据，改写指令 = 版本提示词**。

## 四、三个集成方案

### 方案 A：纯业务数据（✅ 我推荐）
- 真实测试例 `input_payload` 只放 **4 输入字段**（name/persona/product_info/original_script），**不带 messages**。
- 符合既定架构（测试例=纯数据），数据干净，和 generator 实际行为一致。
- **附带**：写个一次性清理，把现有 demo case 的 `messages` 字段也移除（让全系统一致），seed 脚本同步改。
- 代价：要动一下 demo seed（小改，纯数据规整，不碰业务代码）。

### 方案 B：保留 messages（维持现状）
- 给真实数据也**补上 messages**（我按产品信息自动生成一句仿写指令），和 demo 保持一致。
- 代价：延续"指令混在测试例"的死字段问题，将来还是要清。

### 方案 C：折中（真实数据干净，demo 暂不动）
- 真实数据只放 4 输入（同 A）；demo case 的 messages 暂留（demo 本就是占位，等整体重构）。
- 代价：真实/demo 数据结构暂时不一致，但 demo 标了 tag 易识别。
