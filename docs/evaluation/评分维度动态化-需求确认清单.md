## ② "主播分组"的真实粒度：按红人 vs 按业务组合 ⚠️ 同一会议内两种表述

**0717 张翀原话（按红人）**：
> "他提他的那个维评分维度可能都会不一样"（语境：慧敏一个测试集、邓紫棋一个测试集）

**0717 讨论收敛后（按业务组合，更晚）**：
> 张翀："工作台其实有可能我们也有各种组合配置……不过100种那么多，可能会**四五种**。"
> 尹志伟："**七八种**。对你是四五种七八种，但是最后出来是100个200个实例这样的呀……你有多少网红就都有多少实例啊。"

**0720 v2 设计稿采用**：组合口径——`scenario_tag`（业务场景变体）+ 策略层组合（`test_case_selector` / `dimension_weight_overrides` / `rubric_selector`），**无 per-红人 字段**（`kol_id` 仅在"未来扩展"表里出现一次）。

**差异**：按红人（100+ 套）vs 按业务组合（4-8 套）。讨论最终收敛在组合口径，但张翀"每个红人维度可能不一样"的表述意味着个别红人可能需要在套餐之上微调。

**需确认**：
- [ ] ②-a 口径定为「**业务组合套餐**（4-8 种），红人/工作台绑定某个套餐」——红人间无个体差异？
- [ ] ②-b 还是「套餐 + 个别红人可再覆盖一层」（两级：套餐为底、个人微调，类似现有的权重三级覆盖思路）？

**我的建议**：②-a 起步。机制上预留 ②-b 的扩展点（策略绑定关系做成可引用链），但一期不做个人覆盖 UI——避免 4-8 个套餐还没用起来就先做 100 个红人的配置面板。

## ③ rubric 变体的选择时机：策略统一挑 vs 运行时按 case 匹配 ⚠️ 设计稿内部两处表述不一致

**0720 设计稿 §2.8.2（策略统一挑）**：
> "由**策略级 rubric_selector**（按 dimension 选 scenario 变体）启用选择，**而非运行时按 test_case tag 匹配**。一期不做选择，避免评分标准不一致。"

**0720 设计稿 §2.8.1 扩展性预留表（暗示运行时匹配）**：
> "不同达人/品类用不同 rubric：`eval_rubrics` 支持按 `scenario_tag` / `kol_id` **过滤**（未来）"

**差异**：前者 = 一次 run 用一套标准（口径统一、分数可比）；后者 = 同一 run 内不同 case 可用不同 rubric（更细，但 run 内口径不统一，汇总分数的意义存疑）。

**需确认**：
- [ ] ③-a 一期按**策略统一挑**（整个 run 一套 rubric 变体），够用吗？
- [ ] ③-b 是否存在真实场景：同一次 run 里，美妆 case 要用美妆 rubric、食品 case 要用食品 rubric（即必须运行时按 case 匹配）？

**我的建议**：③-a。理由：(1) 版本对比的核心价值是同口径比较，run 内混标准会让"整体平均分"失去意义；(2) 真有按品类细评需求时，按品类**分两次 run**（各自绑各自策略）即可达成同样效果且口径更清晰；(3) 张翀说的"业务需要强展示/强背书"是**业务级**差异，恰好是策略级粒度。

## ④ 评分规则（rubric/维度）自身的迭代追溯 ⚠️ 从未讨论过（新增议题）

**现状**：所有会议与文档都**没有**涉及"评分规则改版后，历史分数怎么办"。当前实现：
- rubric / 维度权重改动**直接生效**，无版本概念
- 历史 run 的 `eval_scores` 只存了分数，**没存"当时用的哪版规则"**
- 版本对比页对比两个 run 时，若期间规则改过，**分数差异混合了"提示词变化"和"规则变化"两个因素**，无法归因

**需确认**：
- [ ] ④-a 要不要做规则的**版本化/快照**？
- [ ] ④-b 若做，粒度到什么程度：仅 run 的 metadata 里存规则摘要（轻量，够展示"本 run 用的规则版本"）？还是完整快照（可重放/重算历史分数）？

**我的建议**：④-a 做，④-b 取轻量方案——run 创建时把「维度集 + 权重 + rubric 内容摘要 + 规则版本号」快照进 `run.metadata`，对比报告若两 run 规则版本不同则**显著标注**（"规则已变更，对比仅供参考"）。不做重放（ROI 低——重放历史分数不如直接重跑一次 run）。
