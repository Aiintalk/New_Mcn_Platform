## 2. 结论摘要

本轮反馈中，确认存在 4 组需要修复的产品或代码缺陷：

1. 红人工作台的“新增红人”入口实际进入人格定位，既不创建正式红人，也没有生成后的工作台去向，入口承诺与实际行为不一致。
2. 千川脚本预审只校验人工智能返回内容能否解析为 JSON，没有校验结果结构；异常结果可能被当成成功，前端随后空白或渲染失败。
3. 千川脚本复盘的生成流即使报错或没有有效报告，后台任务仍会被标记为成功，前端也不能识别流中的错误文本。
4. 千川剪辑预审在截帧成功、转录失败时保留半成品状态，而且只要任一侧有帧或文案就允许开始分析，导致不完整输入被当作可预审输入。

“千川文案预审不能粘贴”在最新代码中暂未确认：当前页面已有两个可编辑文本框，支持直接粘贴。该问题先作为线上版本核对项，不在未复现前直接改业务代码。

“固定提取 8 帧”“卖点提取浅”“仿写内容接近原文”“报告建议不够专业”等属于输出或分析方案调优，不纳入本缺陷修复版本。

| 等级 | 定义 |

| A | 已在可用环境复现，并由代码定位根因 |

## 5. 目标与非目标

### 5.1 本期目标

- 消除“没有有效输出但页面或任务表现为成功”的情况。
- 任何人工智能失败、返回空内容或返回格式错误，都给运营明确、可持续查看的失败原因和重试入口。
- 不丢失运营已经上传或粘贴的输入，失败后可直接重试。
- 修正红人工作台“新增红人”入口的错误承诺，并补齐人格定位完成后的去向。
- 保证后台任务状态、页面状态和实际业务结果一致。

### 5.2 非目标

- 不调整卖点提取深度、提示词和模型输出风格。
- 不改千川仿写算法、相似度和单次生成数量。
- 不在本期改造剪辑分析的固定 8 帧策略；是否改为动态帧数或完整视频分析放入输出调优版本。
- 不以“返回一份报告”为标准解决报告质量问题。
- 不新增运营创建正式红人的权限，不改变现有管理员创建、运营使用正式红人的权限边界。
- 不做与本轮缺陷无关的页面视觉重构。

## 6. 详细需求

### 6.1 BUG-01 红人工作台入口与人格定位去向不一致

#### 6.1.1 当前事实

- 红人工作台右上角按钮显示“+ 新增红人”，点击后直接进入人格定位页。
- 人格定位页必须从正式达人列表选择已有 `kol_id`，只会把报告同步给该达人，不会新建 `kols` 记录。
- 生成结果页只有导出、复制、优化和重新开始，没有“进入该红人工作台”或“返回红人列表”。
- 正式红人新建当前只存在于管理员的“红人管理”，后端接口也要求管理员权限。

#### 6.1.2 根因判断

Sprint25 将人格定位改为绑定已有正式达人后，红人工作台旧的“新增红人”文案和完成态导航没有同步收口。问题不是生成失败，而是入口仍承诺会创建红人。

#### 6.1.3 解决方案

1. 运营端红人工作台将“+ 新增红人”改为“人格定位”，仍进入现有人格定位页。
2. 不允许人格定位隐式创建正式红人，也不得根据姓名自动创建或匹配红人。
3. 管理员继续在“红人管理”创建正式红人；本期不向运营开放创建权限。
4. 人格定位选择目标达人后，页面持续保留该 `kol_id`。
5. 报告生成及档案同步完成后，结果页增加两个明确动作：
   - “进入红人工作台”：进入当前 `kol_id` 的红人工作台人物档案页；
   - “返回红人列表”：回到运营端红人工作台列表，并刷新列表数据。
6. 生成或同步失败时，不展示“完成”去向；保留本次输入和已选达人，允许重试。
7. 管理员视角可在运营页提供“前往红人管理新增”的入口，但不得在运营角色下显示无权限入口。

#### 6.1.4 验收标准

- 运营端不再出现一个实际无法新增红人的“新增红人”按钮。
- 点击“人格定位”进入现有人格定位三步流程，不新建第二套页面。
- 对已有正式达人完成报告后，点击“进入红人工作台”打开同一 `kol_id` 的人物档案。
- 点击“返回红人列表”后，列表正常刷新，且不会凭空出现新的红人。
- 普通运营无法调用管理员创建红人接口。
- 管理员仍可在红人管理正常新增红人，新红人随后能按权限出现在运营列表和人格定位选择器中。

### 6.2 BUG-02 千川脚本预审结束后无结果

#### 6.2.1 当前事实

- 后端只检查人工智能输出能否解析为 JSON。
- 解析成功后直接读取 `rating`、`must_fix`、`suggestions`、`passed`；缺失字段会以空值或空数组返回。
- 前端把 `rating` 当作 `pass`、`minor`、`fail` 三种固定值直接取显示配置；空值或其他值可能触发页面渲染错误。
- 前端在每次提交前清空旧结果；请求失败后只显示短暂提示，页面看起来像回到初始状态。
- 现有测试只覆盖合法评级，没有覆盖缺字段、非法评级和错误数组结构。

#### 6.2.2 解决方案

1. 后端定义严格的脚本预审结果结构：
   - `rating` 必须是 `pass`、`minor`、`fail` 之一；
   - `must_fix` 必须为数组，每项必须包含非空的 `type`、`quote`、`fix`；
   - `suggestions` 和 `passed` 必须为字符串数组；
   - 最终结果至少包含有效评级，数组可以为空但类型必须正确。
2. 人工智能首次输出结构不合格时，最多执行 2 次受控格式修复。格式修复只整理结构，不改变审核结论。
3. 3 次均不合格时，本次审核必须失败：
   - 不写入成功操作日志；
   - 不允许保存到历史；
   - 返回稳定错误码和中文错误说明；
   - 记录任务、模型和失败类型，不记录完整业务文案。
4. 前端收到失败时保留两份脚本、脚本类型和已选商品，展示持续可见的失败面板和“重新审核”按钮。
5. 前端仍做一次防御性结构检查；无效结果不得进入结果组件。
6. 成功日志只能在结构校验通过后写入。

#### 6.2.3 验收标准

- 合法结构正常显示评级、必须修改、建议优化和已通过项。
- 缺少 `rating`、评级非法、数组类型错误、必改项缺字段时，不出现空白页或页面崩溃。
- 纯文本拒答、Markdown 代码块、截断 JSON 均有明确结果：可修复则正常展示，不可修复则明确失败。
- 失败后输入内容不丢失，可原地重试。
- 失败结果不能保存到历史，也不能计入成功审核日志。
- 增加后端异常结构测试和前端错误状态测试。

### 6.3 BUG-03 千川脚本复盘没有输出

#### 6.3.1 当前事实

- 后端生成流异常时，会把 `[ERROR]` 文本写入响应流。
- 流结束后的后台任务无条件写为 `success`，没有区分空流、异常流和有效报告。
- 前端把所有流内容直接拼成报告，不识别错误事件；空流结束后只停止加载，没有失败说明。
- 因此会出现运营看不到报告，但后台任务显示成功，或错误文本可以被保存为报告。

#### 6.3.2 解决方案

1. 后端生成过程必须维护明确终态：`success` 或 `failed`。
2. 只有同时满足以下条件才允许标记成功：
   - 流过程没有适配器、模型或数据库异常；
   - 最终报告去除空白后非空；
   - 生成过程明确发送完成事件，不能只依赖连接自然断开。
3. 异常、空流、半途断流或无效内容必须标记任务失败，并保存稳定失败原因。
4. 流协议返回结构化事件，至少区分：内容、完成、失败。不得再让前端从普通报告文字中猜测 `[ERROR]`。
5. 前端只有收到“完成”事件且报告有效时才展示保存和导出按钮。
6. 失败后保留脚本、文件解析结果和投放数据，展示错误原因、任务编号和“重新生成”。
7. 脚本与投放数据无法匹配时，在调用模型前展示匹配诊断：匹配条数、未匹配脚本、未匹配数据；没有有效匹配时不得生成一份伪报告。
8. 保存接口再次校验任务状态为成功，禁止保存失败任务或错误文本。

#### 6.3.3 验收标准

- 正常流完成后，任务为成功，页面显示报告，可保存和导出。
- 空流、模型异常、网络中断、部分内容后异常时，任务为失败，页面明确提示且不能保存。
- 失败后脚本和 Excel 数据不丢失，可直接重试。
- 报告正文不能包含被当成业务内容的 `[ERROR]`。
- 完全无法匹配脚本和投放数据时，不调用人工智能，并给出可定位到文件行或素材名称的提示。
- 增加正常流、空流、异常流、部分流后失败、数据零匹配和失败任务保存的自动化测试。

### 6.4 BUG-04 千川剪辑预审半完成状态仍可分析

#### 6.4.1 当前事实

- 每侧视频固定先提取 8 帧，再转录文案。
- 截帧成功后立即保存帧；如果转录失败，页面仍显示“已提取 8 帧”，但没有稳定的“转录失败”状态。
- 开始预审只在两侧都完全没有帧且没有文案时阻止；只要任意一侧有帧或文案就可以继续。
- 因此一侧未上传、任一侧转录失败，甚至两侧都只有帧时，也可能进入人工智能分析。

#### 6.4.2 解决方案

1. 每侧视频建立独立处理状态：未上传、待处理、截帧中、转录中、已就绪、处理失败。
2. “已就绪”必须满足：
   - 已选择视频；
   - 截帧成功且至少有 1 帧；
   - 有非空文案，来源可以是自动转录或运营手动粘贴。
3. 两侧都为“已就绪”后才允许点击“开始预审”。
4. 截帧成功、转录失败时：
   - 保留已提取帧；
   - 显示“转录失败，尚未就绪”；
   - 提供“重试转录”；
   - 允许运营粘贴完整文案后转为已就绪。
5. 截帧失败时提供“重试截帧”，不得显示为已处理。
6. 页面显示每侧视频的文件名、时长、帧数、文案字数和当前状态。
7. 人工智能分析返回空内容或异常时，不展示保存、导出按钮；保留两侧处理结果并允许重新分析。
8. 本期继续使用现有 8 帧策略，不将“8 帧”本身判定为缺陷。

#### 6.4.3 验收标准

- 只上传一侧、只处理一侧或任一侧未就绪时，“开始预审”不可用，并明确指出缺少哪一步。
- 截帧成功、转录失败时能看到帧和失败原因，但不能直接预审。
- 手动粘贴非空文案后，该侧可恢复为已就绪。
- 两侧都就绪后可以正常生成报告。
- 分析失败或空结果时，不出现可保存的空报告，输入和处理结果不丢失。
- 增加两侧状态组合、步骤失败、手动文案补救和空报告测试。

### 6.5 VERIFY-01 千川文案预审直接粘贴核对

#### 6.5.1 当前事实

最新代码的原版文案和我方文案区域均有可编辑文本框，并通过输入事件更新内容，页面文案也明确写着“或直接粘贴下方”。因此仅凭当前代码无法确认“只能上传 Word”仍存在。

#### 6.5.2 核对要求

1. 记录线上部署提交号，与本需求核验基线比较。
2. 使用运营账号在 Chrome 和 Safari 分别验证：
   - 键盘粘贴；
   - 右键粘贴；
   - 2000 字以上中文文案；
   - 粘贴后继续编辑；
   - 上传文件后再切换为手动输入。
3. 若线上版本落后且最新代码正常，不为此单独修改业务代码，纳入版本发布说明。
4. 若最新代码仍能复现，再补失败测试并修复输入覆盖层、焦点或浏览器兼容问题。

#### 6.5.3 条件验收标准

- 两侧都能直接粘贴并编辑长文案。
- 粘贴不会触发文件选择，不会被上传区点击事件拦截。
- 上传失败不影响手动输入。
- 不能复现时，验收记录必须写明线上提交号、浏览器版本和测试结果，不得虚构缺陷已修复。

## 7. 共用异常状态规则

本规则适用于 BUG-02、BUG-03、BUG-04，不要求为此进行平台级重构。

1. **成功必须有业务结果**：不能仅以 HTTP 200、流结束或能解析 JSON 作为成功。
2. **失败不清空输入**：运营已经上传、解析、粘贴和选择的数据保留到本次页面会话结束。
3. **失败必须可见**：错误不能只用短暂提示；结果区域要保留失败原因和重试入口。
4. **前后台状态一致**：页面失败时任务不能记成功，任务失败时页面不能开放保存和导出。
5. **不泄露业务内容**：日志记录任务号、模型、阶段和错误类别，不记录完整脚本、报告或视频转录。
6. **不静默降级**：缺转录、缺一侧视频、数据零匹配时不得静默改用残缺输入生成报告。

## 8. 开发拆分与优先级

### 批次一：P0 输出阻断闭环

- BUG-02 千川脚本预审结构校验和失败状态。
- BUG-03 千川脚本复盘流状态和任务终态。
- BUG-04 千川剪辑预审双侧就绪门禁。

批次一完成标准：三项分别完成失败测试、最小修复、相关回归和浏览器证据；不存在无结果成功、失败可保存或输入丢失。

### 批次二：P1 入口语义收口

- BUG-01 红人工作台入口改名和人格定位完成去向。

批次二完成标准：运营、管理员两种角色分别验证入口和权限；同一 `kol_id` 从人格定位进入工作台。

### 批次三：条件性线上核对

- VERIFY-01 文案直接粘贴。

批次三只有在最新代码部署后仍能复现时才进入代码修复；不能复现则只形成核对记录。

## 9. 测试与验收资料

### 9.1 必备测试数据

- 一个普通运营账号及其可见正式达人。
- 一个管理员账号及一个新建测试达人。
- 合法脚本预审 JSON，以及缺评级、非法评级、错误数组、截断 JSON、纯文本拒答样本。

## 10. 发布边界与风险

### 10.1 发布边界

- 本文档完成不代表代码已开发或产品验收通过。

### 10.2 主要风险

- 线上部署版本与最新 `main` 不一致，可能造成反馈现象和代码核验不一致。
- 人工智能供应商可能返回语法正确但业务结构错误的内容，必须以后端结构校验兜底。
- 流式接口若继续依赖响应结束后的无条件后台任务，会重复产生“页面失败、任务成功”的假状态。
- 剪辑预审本期仍使用 8 帧，修复后只能保证输入完整和状态真实，不能承诺分析质量已经完成调优。
